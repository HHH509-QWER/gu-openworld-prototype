# 蛊 · 真人 —— 大世界开放原型

以《蛊真人》世界观为背景的 **大世界探索 + 养蛊炼蛊 + 玩家自由交易** 最小可玩原型。
Godot 4.3+，纯 GDScript，全部界面与场景由代码生成（只需一个 6 行的 `Main.tscn`）。

> ⚠️ **版权提醒（先说清楚）**：《蛊真人》是网络小说作家「蛊真人」的版权作品，2016 年已从起点下架。
> 本项目是**个人学习／技术验证用的同人原型**。若要商业化发行，必须取得原作者或版权方授权，
> 或者把世界观、名词体系改成原创设定（技术架构可以 100% 复用，只需替换 `GameData.gd`）。

| 按键 | 作用 |
| --- | --- |
| `W A S D` / 方向键 | 移动 |
| `E` | 采集脚下的资源点 |

### 核心循环

```
探索采集（灵药 / 精铁 / 兽骨 / 月华露）
      ↓
猎杀妖兽 → 掉落血食、兽骨、精铁
      ↓
在蛊囊里「喂养」蛊虫 → 熟练度 +（血食喂攻伐类蛊虫有 1.5 倍加成）
      ↓
熟练 100 + 月华露 → 蛊虫「升转」，威力按转数大幅提升
      ↓
元石 + 材料 → 蛊师「突破」，真元／气血上限提升
      ↓
自己用不上的蛊和材料 → 和别的玩家当面交易，各取所需
```

### 数值一览（`scripts/GameData.gd` 里全部可调）

* **蛊虫**：月刃蛊 / 火蛇蛊 / 铁骨蛊 / 疾风蛊 / 水幕蛊 / 灵犀蛊 / 春泥蛊 / 血影蛊 / 百步蛊 / 金蝉蛊
  * 每只蛊有 `道`（力道、火道、水道、风道、智道、木道、血道、变化道…）、`转数`、`真元消耗`、`冷却`、`熟练度`
  * 实际威力 = `基础威力 × (1 + 熟练/150) × (1 + (转数-1) × 0.6)`
* **蛊师转数**：一转 100 真元 / 120 气血 → 五转 680 / 680；突破需元石 + 材料
* **妖兽**：铁甲猪（弱）、青纹蛇（快）、赤目狼（强），被击杀 20 秒后在别处重生

### 网络模型：主机权威（Host-Authoritative）

安全性是自由交易类游戏的命脉。原型的做法：

* **主机（peer 1）是唯一权威**。元石、材料、蛊虫、采集判定、妖兽掉落、交易结算，全部在主机侧算。
* 客户端只发**意图**：`req_gather` / `req_use_gu` / `req_feed` / `req_trade_set` / `req_trade_confirm` …
* 主机校验后广播**状态**：`net_self` / `net_state` / `net_fx` / `net_trade_state` …
* 每个 `req_*` 都重新校验：距离够不够、是否真的拥有这件物品、冷却好没好、真元够不够。
* 三个内部辅助函数把单机/主机/客户端三条路径统一了：

  | 函数 | 语义 |
  | --- | --- |
  | `_to_host(method, args)` | 本端 → 主机（单机/主机则直接本地执行） |
  | `_srv_broadcast(method, args)` | 主机 → 所有端（含自己） |
  | `_srv_to(pid, method, args)` | 主机 → 指定端 |

* **`_sender()` 这个坑必须记住**：单机模式、以及主机自己的操作，都**不是** RPC，
  此时 `multiplayer.get_remote_sender_id()` 返回 `0`。如果所有 `req_*` 都直接问它，
  单机下采集/用蛊/喂蛊/交易会**全部静默失效**。
  所以本地调用先用 `_local_sender` 记下身份，只有真正的远程调用才去问 MultiplayerAPI。
* **RPC 必须用数组版**：`Node.rpc_id(peer, "m", [a, b])` 会把整个数组当成**一个**参数传过去，
  而不是展开成两个。这里统一用 `MultiplayerAPI.rpc(peer, self, method, arguments)`（`peer == 0` 表示广播）。

* **世界用固定种子生成**，所以各端地形与资源点完全一致，网络里只需要同步「哪些点已被采走」。

### 交易协议（防骗的关键）

1. 客户端 `req_trade_request(target)` → 主机校验双方距离 ≤ 160px，创建会话
2. 双方各自 `req_trade_set(items, stones, gu_uids)` → **主机裁剪报价**（不能报出自己没有的东西）
3. 任何一方改动报价 → 双边 `confirm` 自动清零
4. 双方都确认 → `_execute_trade()`：
   * **再校验一次距离与拥有关系**（防止确认后资产变动）
   * `_extract` 双边扣除 → `_deposit` 双边交付 → 一次性交换蛊虫实体
5. 全程同时只允许一笔交易；断线自动中止

## 四、已知的原型妥协（正式项目必须改）

| 位置 | 现状 | 正式项目应该怎么做 |
| --- | --- | --- |
| 玩家移动 | 各端自算位置，主机只转发 | **服务端权威移动** + 客户端预测 + 回滚校验，防瞬移/加速外挂 |
| 妖兽 AI | 主机单线程模拟 | 分区分帧调度、实体 LOD、专用战斗服 |
| 背包上限 | 无 | 加容量与负重 |
| 掉落归属 | 离尸体最近的玩家 | 伤害贡献权重分配 |
| 世界 | 84×84 格、一次性全量生成 | 分块流式加载 + 服务器分线/跨服 |
| 持久化 | 全在内存，关服即失 | 数据库落库（见下） |
| 反外挂 | 无 | 移动校验、操作频率限制、行为模型 |

### 走向「真正的大世界 MMO」要补的东西

1. **持久化**：PostgreSQL / MySQL 存 `account`、`character`、`gu_instance`（蛊虫是**有唯一 id 的实体**，不是堆叠道具）、`inventory_item`、`trade_log`、`market_order`。所有资产变更写在同一事务里。
2. **真正的拍卖行 / 摆摊**：从面对面交易升级到异步市场——挂单、撮合、手续费（**回收元石的经济水龙头**）、成交历史。这是自由交易游戏的经济核心。
3. **经济系统设计**：必须有足够的**产出（faucet）**和**回收（sink）**。原型里元石只从初始值和交易来，正式版要让元石能从任务/副本产出，并从手续费、突破、炼蛊里被消耗掉，否则必然通货膨胀。
4. **分线与跨服**：单服上限几百人；大世界用「地图分线 + 跨服拍卖行」而不是一张无限大的地图。
5. **移动权威化**：把 `GuPlayer` 的移动逻辑搬到服务端，客户端只发输入。
6. **服务端不用 Godot 渲染**：可以用 Godot 的 `--headless` 模式跑权威端（本原型就是这个思路），或者用 Go / Rust / C# 写独立服务端，Godot 只做客户端。

## 五、想改的话从哪下手

* **加一只新蛊**：在 `GameData.GU` 里加一条，再把名字加进 `GU_ORDER`。如果 `kind` 是新的，在 `Game.req_use_gu` 的 `if kind == ...` 链里加一个分支。
* **加一种材料**：`GameData.ITEMS` + `ITEM_ORDER` + `FEED_VALUE`；想让它能在地图上采到，改 `GuWorld._build_resources`。
* **加一种妖兽**：`GameData.BEASTS` + `BEAST_ORDER`。
* **调数值**：`RANK_ESSENCE` / `RANK_HP` / `RANK_BREAK` / `RANK_UP_COST` 全在 `GameData.gd` 顶部。
* **换美术**：现在全是 `_draw()` 画的几何图形。把 `GuPlayer._draw` / `GuBeast._draw` / `GuWorld._draw` 换成 `Sprite2D` + `TileMapLayer` 即可，逻辑层不用动。
